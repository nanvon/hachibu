# GitHub Release 更新说明

每次发布都在此目录新增一份与 tag 同名的文件，例如发布 `v0.1.0` 时创建 `release-notes/v0.1.0.md`。该文件和版本号一起提交；GitHub Actions 会校验它存在且非空，然后把**全文原样**作为 Release 正文。

Release 标题不做定制，沿用 GitHub 默认的 tag 名（如 `v0.1.0`）。

这不是按时间持续追加的 `CHANGELOG.md`。每份文件只描述一个版本，方便发布前审阅、发布后追溯和重跑 CI。

[highlights.md](highlights.md) 的近期新功能会追加在 Release 正文末尾，见下文「近期新功能」。

应用内更新窗口显示的内容与 Release 正文一致。发布工作流用本版说明和 `highlights.md` 生成 `release-notes.md`，并与 ZIP 更新包和 `appcast.xml` 一起签名上传。HTML 注释不会出现在应用内日志；源文件及 GitHub Release 正文仍保持原样。生成的文件不提交到此目录，也不用维护第二份日志。

## 读者和场景

主要读者是在应用内更新窗口里决定要不要升级的用户。窗口只显示最新一版的说明和近期新功能，跳过几个版本的用户看不到中间各版。所以每一版都要让人读完第一句就知道这版改了什么，条目扫一眼就能找到和自己有关的。

应用内更新窗口是 Sparkle 的标准窗口，按 Markdown 渲染。只用 `- ` 列表、普通段落和行内粗体，不放图片。

## 文件格式

一句话，加一组条目，不分组：

```
现在可以在菜单栏显示电池温度了。

- 在「设置 → 菜单栏 → 菜单栏显示」选择电量、系统功率或温度
- 温度达到提醒阈值时，面板里的温度旁显示「偏高」
- 修复插着电时，偶尔显示为「使用电池」
```

**第一句**

- 说出本版最主要的变化，写用户能得到的结果，30 字以内，以句号结尾。
- 本版有几项同等分量的改动时，第一句概括它们共同的方向，不要用顿号并列。

**条目**

- 每条一件事，40 字以内，结尾不加句号；一般 1～6 条，超过 6 条说明拆得太细或混进了不该写的内容。
- 按对用户的影响从大到小排列。
- 需要用户操作、升级后默认值或行为会变、已有数据会被迁移的，写进相关条目或放在第一条，写清变成了什么、想改回去在哪里改。
- 新功能和位置变化写出入口，用界面上的原名，如「设置 → 通用 → 登录时启动」「检查更新…」。
- 修复以「修复」开头，写用户遇到的现象，如「修复休眠唤醒后，历史曲线的近期图表缺了一段」。
- 条目补充细节，不原样复述第一句。

**特殊情况**

- 只有一处改动时，只写第一句，不列条目。
- 没有用户可感知的改动时，只写：`本版为内部维护更新，功能与上一版一致。` 不要虚构稳定性、性能或功能收益。

**不使用**：分类组头（新增 / 修复 / 优化等）、`#` 标题、加粗小标题、图片、emoji、徽章、下载表格、安装说明等每版重复的固定段落。

## 近期新功能

`highlights.md` 写最近一个月里值得用户知道的新功能，读者是从 Release 页下载、或不常更新的用户，帮他们发现自己可能还没用过的功能。发布时它追加在本版说明后面，中间多空一行；Release 正文和应用内更新内容都是这个顺序。

每次发版写完本版说明后，顺带检查并更新这个文件：

- 第一行固定为 `最近一个月新增的功能，你可能还没用过：`，下面是条目，不写版本号和日期。
- 只写最近约一个月内、特别重要的新功能：用户不知道就用不上、或明显改变使用方式的。修复、后台改进（耗电、性能）、小众或影响面窄的改动不写。
- 每条写清用户能做什么和入口，用界面原名，40 字以内，结尾不加句号。
- 最多 10 条，按重要程度排列。不够就少写，不凑数；没有合适的内容时清空文件，工作流会跳过这一段。
- 本版说明里已经写了的功能不重复写，下次发版再考虑放进来。
- 超过一个月的条目删掉。

## 撰写流程

1. **盘点**：读上一个 `v*` tag 到当前 HEAD 的提交正文，必要时看 diff，重点看界面文案（`.xcstrings` 里的 `zh-Hans` 译文）和文档的改动。逐项记下：改了什么、用户在哪里看到、改之前怎样、改之后怎样、对应哪个提交。这一步只是草稿，不写进文件。
2. **取舍**：去掉用户感知不到的改动——重构、测试、文档、CI、构建脚本、文案微调，以及说不出"用户看到了什么不同"的布局调整。同一件事的多个提交合并成一条。
3. **排序**：找出本版最主要的变化写成第一句，其余按影响排成条目。
4. **写作**：名称以界面上显示的中文为准（`.xcstrings` 的 `zh-Hans` 译文），不用代码里的类名、字段名和内部概念。
5. **自检**：每一句都过下面的问题，有一项不通过就重写或删掉。

## 自检问题

- 不看代码的用户能看懂吗？有没有 IORegistry、遥测、聚合、快照这类内部说法（界面上本来就这么叫的除外）？
- 用户知道在哪里用到、怎么触发吗？
- 写的是用户得到的结果，还是开发做了什么工作？
- 能对应到具体的提交吗？有没有夸大或没做的事？
- 删掉这条，用户会少知道什么吗？不会就删。
- 第一句能单独说明这版改了什么吗？

## 改写对照

| 原写法 | 问题 | 改写 |
|---|---|---|
| 修正 PowerTelemetryData 的 BatteryPower 符号处理 | 内部说法，用户看不懂 | 修复插电放电时，功率流向图把电池画成了用电方 |
| 历史曲线缺口判断不正确 | 读起来像在报告一个现存问题 | 修复休眠唤醒后，历史曲线把休眠前后的点连成了一条直线 |
| 分钟数据聚合改为在事务中执行 | 写了实现过程 | 说不出用户能看到的变化，删掉 |
| 调整设置页布局与文案 | 只说改了哪里，没说变成什么样 | 说不出用户能看到的变化，删掉 |
| 新增温度提醒和健康度提醒，菜单栏可显示温度 | 一条里并列几件无关的事 | 拆成两条，分别写清入口和效果 |
| 通知页支持提醒开关 | 没说能开关什么 | 在「通知」页分别开关电池温度过高和健康度低的提醒 |

## 示例

改动较多的版本：

```
可以在「通知」页设置电池温度和健康度提醒了。

- 电池温度连续 3 分钟高于阈值时发通知，默认 40°C
- 系统最大容量低于阈值时提醒一次，默认 80%
- 系统通知未允许时，「通知」页给出打开通知设置的按钮
```

带有行为变化的版本：

```
历史曲线的近期图表可以查看 7 天了。

- 超过 7 天的分钟数据会合并为每小时一条，升级后首次启动时自动完成
- 修复休眠唤醒后，历史曲线把休眠前后的点连成了一条直线
```

只有一处改动的版本：

```
「设置 → 通用」新增「登录时启动」。
```
