# Hachibu v2 充电控制技术调研

调研日期：2026-10-22。

本文是技术调研记录，不是已确定的 v2 实施设计。调研阶段只读核对仓库、公开资料、开源代码及本机配置，未修改文件、启停应用、调用 helper、探测 SMC 控制 key 或改变充电状态。本文按后续要求保存；以下本机数据为调研时的快照。

## 本机只读探测补充（2026-10-23）

环境：MacBookPro18,1（M1 Pro），System Firmware 20457.1.29，macOS 27.0.1（26A434），AlDente 1.39.3 及其 helper 正在运行。只发读取命令，未写入任何设置。

- SMC（普通用户，只发 KeyInfo 和 Read）：CH0B、CH0C、CHTE、CHWA、CH0I、BCLM 返回 -124（key 不存在）；CH0J、bfF0、bfD0、bfE0 在 KeyInfo 阶段返回 `0xe00002c1`（kIOReturnNotPrivileged）；CHIE 存在，类型 `hex_`，大小 1，当前值 `00`。这个固件号与 batt issue #152 记录的固件相同。结论：本机已不能用传统 SMC key 暂停充电，第 1 节表中“传统 SMC 暂停充电”在本机不可用，只剩切断适配器供电。
- PowerUI：`PowerUISmartChargeClient` 普通用户可读，结果为支持、已开启、上限 80、可选值 80/85/90/95/100，方法类型编码见 `docs/v1技术设计.md` 第 6 节。第 3.4 节“只作为研究候选”的判断据此调整：只读接口已在 v1 中使用，并有类型编码校验和退回读文件的处理；写入接口仍待实验。
- powerd 文件：`ChargeCtrlPolicy{reason=manualChargeLimit, soclimit=80, owner=455}`，pid 455 为 `/usr/libexec/PowerUIAgent`，即系统设置写入的原生上限，与 AlDente 无关。
- 系统设置 URL `x-apple.systempreferences:com.apple.preference.battery` 有效：PowerPreferences.appex 的 `legacyBundleIdentifier` 包含 `com.apple.preference.battery`。

据此，v2 的推荐范围见 `docs/v1技术设计.md` 第 18 节。待验证项：PowerUI 写入是否需要特权；ad-hoc 签名的 App 能否用 `SMAppService.daemon` 注册 helper；退出 AlDente 后原生上限的实际充电行为。

## 1. 结论

v2 有可行路径，但“root helper 写 SMC”已不能作为所有 Apple Silicon 的通用方案。对当前机器，建议先验证 Apple 官方捷径限充，再确定自定义控制的支持范围。

| 路径 | 能力与边界 | 建议 |
|---|---|---|
| 系统原生上限＋Shortcuts | macOS 26.4+、Apple Silicon，原生范围 80%–100% | 优先验证 |
| 传统 SMC 暂停充电 | 可由程序实现阈值和恢复下限，但受固件权限限制 | 按实际能力支持 |
| 特定固件的上下限控制 | 固件自行管理阈值，仅部分版本存在 | 单独验证 |
| 切断适配器供电 | 电脑改用电池，到下限再恢复供电 | 不作为自动兼容替代 |
| 私有 PowerUI 接口 | 已有开源实现，但接口未公开 | 暂不优先采用 |

macOS 14–26.3 不具备上述原生限充功能，若要支持，需要单独验证其他后端。支持范围不能只按 CPU 型号或 macOS 主版本判断，还要考虑固件和实际权限。

## 2. 系统原生限充与 Shortcuts

Apple 官方确认，原生 Charge Limit 支持 Apple Silicon、macOS 26.4+，设置范围为 80%–100%。接近上限时停止充电，电量下降超过约 5% 后恢复，系统偶尔仍会充到 100%以维持电量估算准确。因此它不能承诺“绝不超过设定值”。[Apple 充电上限说明](https://support.apple.com/en-us/102338)

Apple 已提供 `Set Battery Charge Limit` 捷径动作，平台包含 macOS，并正式支持通过 `shortcuts run` 执行捷径。Hachibu 可以先验证调用用户配置的固定限充捷径，无需自行安装 root helper。[Shortcuts 更新说明](https://support.apple.com/en-us/125148)、[命令行调用说明](https://support.apple.com/guide/shortcuts-mac/run-shortcuts-from-the-command-line-apd455c82f02/mac)

命令形式如下，仅作为后续集成说明，本次未执行：

```sh
shortcuts run "用户配置的限充捷径名称"
```

Apple 文档说明，命令成功退出码为 0，错误为 1；如果捷径需要用户输入，命令会等待交互。退出码只能反映执行结果，不能单独证明硬件已经停止充电。

目前仍未验证：

- 动作的具体参数、是否支持变量及完整输入范围。
- 首次授权、后台调用和锁屏时的行为。
- 设置跨应用退出、睡眠、重启和关机的完整持久性。
- Hachibu 调用后，系统策略读回和实际充电行为是否符合预期。

目前只能确认存在公开路径，尚不能宣布 Hachibu 集成已可用。此次未找到可直接供独立 Swift 应用使用的公开限充 SDK API，这不否定 Shortcuts 路径。

## 3. SMC 控制与固件边界

### 3.1 已核对的控制机制

传统 `CH0B`／`CH0C`、`CHTE` 控制的是允许或暂停给电池充电，阈值和恢复下限由程序维护。`bclm` 的 arm64 `CHWA` 路径只提供 80%／100% 两种状态，Intel 的 `BCLM` 百分比写入不能用于本项目。[batt 充电实现](https://github.com/charlie0129/batt/blob/4574ecb0f3b2d5f1829154a2aae89c3cc3b0b716/pkg/smc/charging.go)、[bclm 架构分支](https://github.com/zackelia/bclm/blob/ae2c209614755d81bf5b788513dba1d44280a6f6/Sources/bclm/main.swift)

已核对的底层调用通过系统现有 AppleSMC user client 完成，没有安装自定义内核扩展的调用路径：

```text
AppleSMC service
→ IOServiceOpen(device, mach_task_self(), 0)
→ IOConnectCallStructMethod(conn, 2, SMCKeyData_t)
→ SMC KeyInfo / read / write
```

来源：[gosmc 底层调用](https://github.com/charlie0129/gosmc/blob/36c917295717bb50f098b591843eb23b4ca699dd/driver_darwin.go)。

### 3.2 root 不能保证新固件可写

`batt` 的调查记录了 macOS 27 新固件中传统 key 变为空占位、另一组控制 key 即使 root 也返回 `kIOReturnNotPrivileged`。项目将其归因于 Apple 私有 entitlement `com.apple.private.iokit.soc-limit`。这是开源项目的复现及调查结论，尚非 Apple 官方兼容性说明，也不能据此判定本机一定受影响。[问题记录 #152](https://github.com/charlie0129/batt/issues/152)

因此，key 存在不等于可写；安装 helper、取得管理员批准、签名或公证，也不能据此推导为可控制。本次没有验证本机固件及 SMC 控制能力。

### 3.3 切断适配器供电不能等同于暂停充电

`batt` 的适配器替代方案通过切断外接供电实现低于 80% 的控制，作者在 M5 Air 上验证过。这会实际使用电池并产生充放电循环，与“暂停充电、继续由充电器供电”不同。不能为了兼容而静默切换到这种行为，也不能将该设备上的结果外推为本机已支持。[方案与实测 PR #154](https://github.com/charlie0129/batt/pull/154)、[适配器实现](https://github.com/charlie0129/batt/blob/4574ecb0f3b2d5f1829154a2aae89c3cc3b0b716/pkg/smc/adapter.go)

### 3.4 私有 PowerUI 接口只作为研究候选

`batt` 当前还有通过私有 `PowerUI.framework`、`PowerUISmartChargeClient` 操作系统原生上限的实现。它动态检查能力和可选值，不能视为稳定公开 API。公开产品应先验证官方 Shortcuts 路径。[PowerUI 实现](https://github.com/charlie0129/batt/blob/4574ecb0f3b2d5f1829154a2aae89c3cc3b0b716/pkg/powerui/powerui.m)、[后端选择](https://github.com/charlie0129/batt/blob/4574ecb0f3b2d5f1829154a2aae89c3cc3b0b716/pkg/daemon/compatibility.go)

## 4. 特权 helper 与 XPC

[v1 技术设计第 18 节](v1技术设计.md#18-为-v2v3-预留) 已规划 `SMAppService.daemon`＋XPC。对需要 SMC 的后端，这个方向仍然合适。它负责特权服务，与 v1 登录启动的 `SMAppService.mainApp` 分开；原生 Shortcuts 后端不必因此安装 Hachibu 的 root helper。[SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice)

现代注册方式将 LaunchDaemon plist 和可执行文件随 App 打包，通过 `SMAppService.daemon(plistName:)` 注册并由用户批准，不必沿用复制到 `/Library/PrivilegedHelperTools` 的旧式布局。[Apple helper 迁移指南](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos)

以下是设计建议，尚未实现：

- helper 只暴露查询能力、设置策略、解除本应用干预等业务操作，不开放任意 shell、文件路径或 SMC key/value。
- App 与 helper 双向校验 Bundle ID、Team ID 和签名要求。仅校验同一个 Team ID 不足以限定调用方。
- helper 自己校验数值范围和状态转换，并串行执行控制；不能依赖客户端 UI 校验。
- 分别判断服务授权、XPC 可达、协议匹配和硬件控制能力；`SMAppService.status == .enabled` 不能证明所有环节可用。

最低 macOS 14 可以使用公开的 `NSXPCListener.setConnectionCodeSigningRequirement(_:)` 和 `NSXPCConnection.setCodeSigningRequirement(_:)`，无需采用仅根据 PID 查签名的方案。[监听端校验](https://developer.apple.com/documentation/foundation/nsxpclistener/setconnectioncodesigningrequirement(_:))、[连接端校验](https://developer.apple.com/documentation/foundation/nsxpcconnection/setcodesigningrequirement(_:))

调研时工程默认使用 ad hoc 签名。v2 需要单独安排开发签名方式，不能为了开发方便让 root helper 接受任意本地签名客户端。

## 5. 退出、异常、睡眠与卸载恢复

以下为建议行为，具体硬件保持和复位能力仍需按后端验收：

| 场景 | 建议行为 |
|---|---|
| 正常退出 | SMC 后端默认解除本应用干预；是否允许退出后继续控电，另作明确选项 |
| App 崩溃 | helper 根据连接失效或租约超时释放控制 |
| 睡眠、唤醒 | 按后端验证保持能力；唤醒后重新读取，不能依赖睡眠期间的计时器 |
| 禁用、卸载、更新 helper | 先解除控制并确认，再注销服务 |
| 强杀 helper、断电、恢复写入失败 | 不能保证立即恢复，需要下次启动恢复和手动解除入口 |

Apple SDK 明确 `unregister()` 会终止运行中的 daemon，不会替应用恢复 SMC。正确顺序应为：停止新请求 → 经 XPC 解除本应用控制 → 确认回复及相关读回 → 注销 helper。不能先卸载 helper，再期待它清理硬件状态。[unregister()](https://developer.apple.com/documentation/servicemanagement/smappservice/unregister())

该具体终止语义也已在调研机的 Xcode SDK 中核对：

```text
/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/System/Library/Frameworks/ServiceManagement.framework/Headers/SMAppService.h
```

“恢复”应指解除 Hachibu 的干预，不能承诺立即开始充电。系统温控、原生上限和适配器条件仍可能阻止充电。

原生限充属于系统设置，退出时保留还是恢复需要单独决定；恢复时不能覆盖用户后来修改的值。异常退出不会执行正常清理，不能仅依赖 App 的退出回调。[NSXPCConnection](https://developer.apple.com/documentation/foundation/nsxpcconnection)、[launchd 服务说明](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)

## 6. 本机配置与 AlDente 共存

### 6.1 本机只读快照

| 项目 | 调研时结果 |
|---|---|
| 系统 | macOS 27.0.1，build 26A434 |
| AlDente | 1.39.3，build 111 |
| AlDente 服务文件 | 存在 `com.apphousekitchen.aldente-pro.helper` 的 LaunchDaemon plist 和 helper 文件 |
| 机型 | 仓库设计记录为 MacBookPro18,1（M1 Pro）；本次 `hw.model` 查询被沙箱拒绝，未独立确认 |

服务文件存在不能证明服务正在运行或持续控制充电。

只读解码 `/Library/Preferences/com.apple.powerd.charging.plist` 的 `policies` 后，实际为 `NSKeyedArchiver` 归档，包含以下策略字段：

```text
ChargeCtrlPolicy
reason = manualChargeLimit
soclimit = 80
drain = true
terminated = false
noChargeToFull = false
isEndOfCharge = true
```

这只是保存的策略，不能证明设置者或硬件实时执行结果。未公开字段的含义不能按名称直接认定，也不应通过直接编辑该文件控制充电。

### 6.2 多个控制工具不应同时接管

AlDente 官方提供退出后保留暂停充电的选项，所以退出 AlDente 不足以证明它已解除控制。后续实验前，应明确恢复它的默认控制状态，再由 Hachibu 接管，避免两套工具争用。[AlDente 功能说明](https://apphousekitchen.com/aldente-overview/features/)

AlDente 1.39 发布说明明确为 macOS 27 重写充电控制，因此旧版公开实现不能代表当前实现。官方 FAQ 建议它控电时将系统上限设为 100%、关闭 Optimized Battery Charging，以免互相影响；这属于 AlDente 的使用建议，不应直接推广为所有 Hachibu 后端的统一要求。[AlDente 1.39 发布说明](https://github.com/AppHouseKitchen/AlDente-Battery_Care_and_Monitoring/releases/tag/1.39)、[官方 FAQ](https://apphousekitchen.com/faq/)

Hachibu 的共存策略建议：发现其他工具可能仍在控电时保留监控能力，不自动启动第二套控制。仅凭进程存在与否，无法完整判定硬件策略是否已经清除。

## 7. 对 v1 的影响与后续验收

当前 v1 可以继续实现，无需为本次调研调整代码。现有 `BatterySnapshot.chargeLimitPercent` 保持“系统上限”含义；v2 另行记录目标值、控制后端、授权状态和执行结果。[字段定义](../Packages/HachibuKit/Sources/BatteryCore/BatterySnapshot.swift)

后续建议按以下顺序推进，均未在本次执行：

1. 单独验收原生 80%／100% 捷径，确认参数、授权、后台调用、策略读回与实际行为。
2. 决定低于 80%、自定义恢复下限、旧系统支持是否进入 v2 首版。
3. 如需 SMC 后端，再验证本机固件、权限和具体控制能力；区分命令接受、状态读回和实际充电变化。
4. 验收正常退出、App 崩溃、helper 异常、睡眠唤醒、重启和卸载恢复。

写 SMC、安装 helper、执行捷径或改变充电状态属于后续控制实验，需要另行明确安排。本次没有验证任何本机控制能力。
