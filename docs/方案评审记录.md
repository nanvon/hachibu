## 1. 充电接管的模型（最主要的一条）

### 1.1 现状的问题（意见，依据为已读代码）

“打开时接手、退出时还给系统”（设计文档 21.1、21.4）是照 AlDente 的旧行为定的。AlDente 当年必须常驻，是因为它靠 SMC 反复干预充电。现在的上限由 powerd 和固件执行，写入后不需要进程在场。继续按“运行时才生效”设计，带来这些复杂度：

- 保存接管前的原值（`managedOriginal`），退出、崩溃、切换模式时恢复（`restoreManagedLimitBeforeExit`、`restoreManagedOriginal`）。
- helper 的续约、标记文件和超时恢复（`Helper/main.swift` 的 `leaseDeadline`、`tick`、`performRelease`）。
- 每次退出都释放一次，下次启动再写回。目标低于 80% 时释放要先关闭上限，文档 21.2 记录关闭后约 2 秒开始充电。Sparkle 更新重启是否也走 `applicationWillTerminate`，需核对。
- 系统设置里改了值，要判断是否“被别处改过”并改回（`managedAppliedLimit`、`hasRevertedExternalChange`、`externalChangeRevertedAt`）。
- 两种模式并存，切换时要丢弃“保持当前电量”的状态（`chargeControlDidChange`）。

### 1.2 建议的模型（意见）

只保留一种模式：Hachibu 的上限就是系统的上限，范围 20–100%，写入后一直有效。

- 80–100%：与现在的“跟随系统设置”相同，不需要 helper。
- 低于 80%：经 helper 写一次，不续约，不超时恢复。
- 系统设置里改了值，Hachibu 跟着变，不改回。
- 只有临时状态需要自动返回：校准、保持当前电量、充满一次（见 5.1）。中断或超时后回到用户的目标上限，不是接管前的原值。续约只为这些状态保留。
- 停止使用只发生在移除 Helper 时：把上限改回 80% 以上。

可以删掉：`ChargeControlMode`、`managedOriginal`、退出时恢复、稳态续约、外部修改改回和提示、“退出后保留当前上限”选项。

代价：放弃 `新功能需求.md` 第 6 节的需求“运行期间系统设置的改动不影响应用”。需要用户确认。

### 1.3 前提实验（未做）

设计文档 21.9 的待验证项“使用电池超过 5 分钟再插电”：系统撤销登记后，再插电时是系统按偏好自己重新登记，还是需要再写一次。

- 系统自己重新登记：1.2 直接成立。
- 需要再写一次：必须有常驻进程。这时建议把控制逻辑放进 helper（开机即运行），App 只做界面，校准等在 App 退出或更新期间继续，结构与 batt 相同。代价是 root 进程里的代码变多；XPC 接口仍只开放设目标、开始和停止校准等有限操作。

同一实验里顺便确认：重启后、睡眠唤醒后登记是否保留（也在 21.9）。

### 1.4 核对要点

- 1.1 列的每个函数和标志位是否确实只为“运行时才生效”服务，有没有别的用途。
- 单一模式下，设计文档 21.5 的系统策略处理、第 6 节“保持当前电量”的规则哪些要改。
- 已发布版本的用户设置（`chargeControlMode`、`managedLimitOnQuit`、`managedChargeOriginal`、helper 标记文件）怎么迁移。

## 2. Helper 的风险

### 2.1 续约截止时间计入睡眠（已读代码；后果为推断）

`Helper/main.swift`：`leaseDeadline` 是 `Date`（第 16 行），`tick()` 用 `Date() > deadline` 判断（第 242 行）。合盖超过 `ChargeHelper.leaseTimeout`（300 秒）后唤醒，截止时间已过。

App 侧续约在 `BatteryMonitor+ChargeControl.swift` 的 `startChargeControl`：`Task.sleep(for: 30 秒)` 循环调用 `renewLeaseIfNeeded`。helper 的检查是 15 秒的 Dispatch 定时器。唤醒后谁先执行没有保证。全仓库没有 `beginActivity` 或关闭 App Nap 的代码，App 的定时器可能被系统推迟。

helper 先到的后果：`performRelease` 关闭上限、恢复原值、删标记；App 之后读回不一致，按“被别处改过”写回并提示。期间可能按原值充电。

建议：helper 的截止时间改用不计睡眠的单调时钟（如 `DispatchTime`、`CLOCK_UPTIME_RAW`）。如果采用 1.2，稳态不再续约，这个问题只剩临时状态。

核对要点：`Task.sleep(for:)` 默认时钟在睡眠期间是否前进；Dispatch 定时器 `.now()` 基准在睡眠期间是否前进；验收文档“唤醒和重启”一行的真机结果。

### 2.2 续约条件依赖读回值（已读代码）

`renewLeaseIfNeeded` 用 `snapshot.chargeLimit` 是否低于 80 决定续不续。系统临时充满期间上限读数为 100（设计文档第 6 节），这时不续约，5 分钟后 helper 会执行释放并写 PowerUI，而 App 自己在临时充满期间是刻意不写入的。建议改为按“目标低于 80 或有标记文件”续约。影响小，属于边界情况。

### 2.3 装过 Helper 后的提权路径（推断，未验证）

依据是设计文档 21.3 的实测记录：

- 0.1.11 换成 0.1.12 后，新 label 注册即为已允许，不用重新批准。
- ad-hoc 签名没有 Team ID，系统忽略 `AssociatedBundleIdentifiers`。
- 同一 bundle id 有多份副本时，系统可能按另一份记录 cdhash、按另一份的路径启动。

由此推断：用户批准过 Hachibu 的后台项目后，任何以该用户身份运行的进程，可以做一个同 bundle id 的 App，带自己的 LaunchDaemon plist 和可执行文件，调用 `SMAppService.daemon(plistName:).register()`，不经密码得到一个 root 进程。另外 `/Applications/Hachibu.app` 是拖拽安装的，归用户所有，包内文件可被同用户进程改写（系统的“App 管理”权限是否拦截 ad-hoc 签名的 App，未确认）。

helper 自身的 XPC 接口很窄（只能设 1–99 的上限、释放、续约），调用方校验弱不是主要问题；问题在批准记录可被借用。

验证方法：另做一个测试 App，bundle id 相同、放在其他路径、带不同的 helper 和新 label，在已批准 Hachibu 的机器上注册，看是否直接为已允许并以 root 运行。按记忆里的约定，改系统状态的操作先说明范围、等用户确认，不用 `sfltool resetbtm`。

成立时的两个解法：

- 使用 Developer ID 签名（见第 7 节）。
- 不用 `SMAppService`：安装时请求一次管理员密码，把 helper 放到 root 所有的 `/Library/PrivilegedHelperTools`，plist 放 `/Library/LaunchDaemons`。没有可借用的批准记录，可执行文件也不能被普通进程替换。代价是安装和每次 helper 变化都要输密码，并要自己写安装、升级、卸载。

### 2.4 每个版本一个 label（已读代码）

`Config/Base.xcconfig` 的 `HACHIBU_HELPER_LABEL` 带 `MARKETING_VERSION`，每个版本在后台项目数据库留一条记录（设计文档 21.3 已说明）。`Helper/Info.plist` 嵌入版本号，所以即使 helper 源码没变，每个版本的二进制也不同。如果继续用 `SMAppService`，可以考虑让 label 跟 helper 的内容走而不是跟 App 版本走，前提是 helper 的构建产物在源码不变时保持一致，需验证。采用 2.3 的任一解法后这条不再需要。

## 3. 发布链路（已读代码）

更新通道通向所有用户，其中一部分装了 root helper。

- `.github/workflows/release.yml`、`ci.yml` 里的 Actions 都按 tag 引用：`actions/checkout@v4`、`actions/cache@v4`、`maxim-lobanov/setup-xcode@v1`、`softprops/action-gh-release@v2`、`dorny/paths-filter@v4`。建议固定到 commit SHA。发布 job 里有 `SPARKLE_PRIVATE_ED_KEY`，同一 job 中更早的第三方 Action 可以改动工作区或 PATH。
- `project.yml` 的 Sparkle 是 `from: 2.10.0`。`.xcodeproj` 不提交，仓库里只有 `Packages/HachibuKit/Package.resolved`，App target 的依赖没有锁定文件，每次发布解析到当时最新的 2.x。建议改成精确版本。
- XcodeGen 的 zip 用 `curl` 下载后没有校验哈希；`dmgbuild==1.6.7` 固定了版本但没有哈希。
- `xcode-version: latest-stable`，不同时间的构建用的 Xcode 可能不同。

发布前确认 tag 对应提交通过测试的问题，补充见 11.3。

## 4. 耗电（已读代码；实际影响未测量）

- `BatteryMonitor.swift` 的 `smcInterval`（约第 235 行）：面板关闭时每 1.5 秒读一次 `CHSC`，不区分是否插电。未插电时充电状态不会变化，插电有 `IOPSCreateLimitedPowerNotification`。建议未插电时停掉这个循环；插电且状态稳定时是否放宽间隔，由用户按菜单栏图标的响应要求决定。
- 每次读取都调用 `publish()`，再进入 `evaluateChargeControl()`。
- `refreshHelperIfNeeded` 每 30 秒在主线程读一次 `SMAppService.status`，没装过 helper、没开接管模式时也读。
- 接管模式下每次完整读取后运行一次 `pmset -g battlimit`（面板关闭时约每分钟一次）。可以改成只在写入后、唤醒、插拔、读回值变化时读。

建议先用 `powermetrics` 或活动监视器的能耗数据测量面板关闭、使用电池时的唤醒次数，再决定改动范围。

## 5. 功能

### 5.1 充满一次（意见）

设计文档第 6 节的结论是不做，原因是系统的 `temporarilyDisableMCL:` 期间读数与“用户设为 100”无法区分。如果目标上限由 Hachibu 自己保存（接管模式或 1.2 的模型），可以不用系统的临时充满：把上限临时写成 100，充满或拔电后写回目标。它和校准、保持当前电量一样是“到条件后回到目标”的临时状态。

`新功能需求.md` 第 1 节和待定事项已有。可以经 helper 把上限临时写成当前电量。建议等 1.2 定下来再做，与 5.1 共用临时状态的逻辑。

### 5.3 自动化入口（已读代码）

仓库里没有 AppIntents、URL scheme（`CFBundleURLTypes`）或命令行工具。可以加快捷指令动作：设上限、充满一次、读当前状态。

### 5.4 长期统计（已读代码）

`hourly_samples` 永久保存，设计文档第 10 节写明界面不读。可以用来显示高电量时长、高温时长等。

## 6. 结构

### 6.1 充电控制的编排（意见，依据为已读代码）

校准是纯状态机（`CalibrationEngine`），`ManagedChargeLimit`、`ChargeLimitHold` 也有纯函数部分。但整体编排在 `BatteryMonitor` 和它的扩展里，靠多个互相影响的可变标志协调：`isWritingChargeLimit`、`isRemovingChargeHelper`、`managedLastWrite`、`managedAppliedLimit`、`managedWriteFailed`、`hasRevertedExternalChange`、`restoredForOtherTool`、`chargeLimitHoldPausedUntil`、`restoresChargeLimitHoldFirst`。

建议收成一个纯函数：输入当前状态、读数、设置和时间，输出新状态和要执行的写入。再写一个模拟 powerd 行为的假系统，用随机事件序列（插拔、睡眠、外部改值、系统策略、写入失败、崩溃重启）检查不变量，例如系统策略期间不写入、同一值的重写间隔、临时状态一定能回到目标。真机上难复现的组合靠它覆盖。如果采用 1.2，状态会少很多，建议先定 1.2 再做这一条。

### 6.2 兼容性（已读文档）

所有字段、SMC key、字节序、PowerUI 类型编码只在 MacBookPro18,1、macOS 27 上验证过（设计文档第 5、16 节）。macOS 14、15 和其他机型未验证。接管和校准从 v0.1.8 起已公开发布，`充电接管与校准验收.md` 的真机验收表大部分为待确认。

建议：界面上把接管和校准标为实验功能；加一个 issue 模板请用户附诊断导出；维护一张机型和系统版本的兼容表。

`v1技术设计.md` 有 945 行，包含 v1–v3 的规格和 19.8 按日期追加的变更记录，文件名仍叫 v1。建议把稳定规格和变更记录分开，减少每次协作要读的量和过期内容。

### 10.2 对 1.3 的补充：实验步骤和一个代码事实

代码事实（已读代码）：`evaluateManagedLimit` 只比较 PowerUI 读回值和目标（`ManagedChargeLimit.isApplied`），不看 `pmset -g battlimit` 的登记。登记丢失而 PowerUI 读回仍等于目标时，Hachibu 不会重写，界面显示“等待生效”或“插上电源后生效”（`ManagedLimitState.resolve`）。所以 1.3 的结果如果是“需要再写一次”，已发布的版本在这种情况下就是失效的，属于要修的缺陷，与是否采用 1.2 无关。

实验要排除 Hachibu 自己的写入。步骤：

1. 接管模式，装好 Helper，目标设为低于当前电量的值（例如电量 70%、目标 60%），“退出后”选“保留当前上限”，然后退出 Hachibu，并确认登录启动是关闭的。
2. 插电状态下记录 `pmset -g battlimit` 和 `pmset -g batt`，确认有 `manualChargeLimit` 的登记、没有在充电。
3. 拔电，保持唤醒 10 分钟，每分钟记录一次 `pmset -g battlimit`，看登记在第几分钟消失。
4. 插电，头 2 分钟每 5 秒记录一次上面两条命令，看登记是否自己回来，以及回来之前有没有开始充电。
5. 同样的初始状态下各做一次：重启后不打开 Hachibu；合盖睡眠 10 分钟以上（插电和不插电各一次）。

### 10.3 对 1.2 的补充：模型改造

这是全文风险最高的一项：改的是已发布用户正在用的设置，并且涉及 root 进程。分三步交付，每步都能编译并通过测试：先改 helper 接口和标记文件，再改 App 的模型和迁移，最后改界面和文档。

**必须保持的规则**（改造前后都成立，写成测试）：

1. `snapshot.activeChargePolicies` 非空时不写入，包括临时状态的自动写入。
2. 其他充电控制工具运行时不写入。现在接管模式会先恢复原值，新模型没有原值，建议只停止写入；临时状态进行中的，先写回用户目标再停。这一点需要用户确认。
3. 同一个值写入后 60 秒内不因读回不一致而重写；写入失败后 60 秒内不自动重试。
4. Helper 不可用时不写低于 80% 的值。
5. 临时充满（`temporaryFullCharge`）期间不写入，退出时也不写。
6. 任何临时状态（校准、保持当前电量、充满一次）在正常结束、取消、App 退出、App 崩溃、断电重启之后，系统上限最终回到用户目标，不停在临时值。最需要保证的是校准第 3 步的 15%。

**谁保存用户目标**（需要用户决定，建议第一种）：

- 平时不保存，系统读回值就是目标；只在临时状态期间保存 `userLimit`，写法与现在的 `ChargeLimitHold` 相同（先保存再写入；系统读回等于自己写的临时值时认为是自己的，变成别的值时认为用户改过，丢弃保存的值、不写入）。好处是“系统设置里改了值，Hachibu 跟着变”不需要额外代码。代价是 Helper 不可用时不能先记下一个低于 80% 的目标等批准后生效，界面上低于 80% 的档位在 Helper 可用前不可选。
- 继续保存 `managedChargeLimit`，系统读回与它不同且不在临时状态时，用系统值覆盖它。保留了“先选后批准”，但又有了两个来源，要处理谁覆盖谁。

**helper 的改动**：

- 现在的标记文件保存的是“第一次覆盖前的系统原值”，恢复时低于 80 的原值按 80（`ChargeHelperMarker.restoredLimit`）。新模型里稳态写入不留标记、不续约；只有临时状态写标记，内容是“超时后回到哪个值”，这个值可以低于 80 或者是关闭。
- 超时恢复的目标可以低于 80% 之后，`performRelease` 不能再一律走“PowerUI 关闭再开启”：回到低于 80% 的值是再写一次偏好并发通知；回到 80% 以上或关闭才经 PowerUI 释放。从 15% 直接改到 60% 时登记是否正确更新，没有实测过，要加进真机验收。
- XPC 接口变化后 `ChargeHelper.version` 加一。label 随 App 版本变化，新 App 只会连到新 helper，不用兼容旧接口。
- `renewLease(seconds: 0)` 表示“退出后保留”的用法随选项一起删除。
- 旧格式的标记文件：Sparkle 更新时旧 helper 发现可执行文件被替换会直接退出，不释放、不删标记（`tick()` 开头）。新 helper 的 `start()` 现在看到标记就设 5 分钟截止时间，到期按旧原值恢复。新 helper 必须能认出旧格式的标记并按下面的迁移表处理，不能按新语义解释，也不能到期恢复成旧原值。

**旧状态迁移**。新版本第一次启动时可能遇到的状态，逐条写测试：

| 旧状态 | 系统里的值 | 处理 |
|---|---|---|
| 从未用过接管模式 | 用户自己的设置 | 不做任何事 |
| 接管模式，上次正常退出，“恢复系统设置” | 接管前的原值 | 把保存的 `managedChargeLimit` 写入一次，读回确认后清除旧键。否则用户的目标会变成接管前的值 |
| 接管模式，“保留当前上限” | 目标值，标记文件 `keepsLimit = true` | 不写入，删除旧标记，清除旧键 |
| 接管模式，上次崩溃或强制退出，目标低于 80% | helper 已按超时恢复成原值，或还没到超时 | 与第二行相同：写入一次目标 |
| Sparkle 更新后第一次启动 | 取决于旧版本退出时是否执行了恢复（1.1 的待核对项） | 与第二行相同；另外处理旧格式标记 |
| 跟随系统设置，但留着 `managedChargeOriginal`（上次恢复失败） | 可能还是旧目标 | 用户的意图是回到原值：按原值恢复一次，成功后清除 |
| 留着 `chargeLimitHold` | 可能是临时值 | 沿用现有的“启动先恢复”规则，`userLimit` 的含义不变 |
| 留着 `calibrationProgress` | — | 沿用现有的“继续 / 放弃”提示；存储格式尽量不改，要改就写解码兼容 |

- 目标低于 80% 而新 Helper 还没批准时（每次更新后 Helper 文件变化，按设计文档 21.3 可能要重新允许），迁移不能完成：保持“待迁移”状态，界面说明，批准后再写入；这期间不要把目标改成 80。
- 迁移要能重复执行：读回确认之后才写完成标志和清除旧键，中途崩溃下次重来。
- 旧键：`chargeControlMode`、`managedLimitOnQuit`、`managedChargeLimit`（按上面的决定）、`managedChargeOriginal`。
- 用户手动装回旧版本时旧版读不到这些键，会按“跟随系统设置”运行，系统里可能是低于 80% 的值。在更新说明里写明。

**一起要改的地方**（已读代码，仍需用搜索核对有没有遗漏）：`ChargeControlMode`、`ChargeControlConfiguration`、`ManagedLimitState`、`AppSettings` 及其测试、`ChargeControlSettings.swift`、`PanelRootView.swift` 的档位写入、`NotificationsPage.swift` 里按模式显示的通知项、`removeChargeHelper()`（移除前把上限改回 80% 以上的规则保留）、String Catalog、设置页和面板的渲染测试、设计文档第 6 节和 21.1、21.4、21.7、21.8、`AGENTS.md` 的版本规划、`新功能需求.md` 第 6 节、README 的卸载说明。

### 10.4 对 2.1、2.2 的补充

我的理解（未在本机验证）：`Task.sleep(for:)` 默认用 `ContinuousClock`，睡眠期间照常前进；Dispatch 定时器用 `.now()`（`DispatchTime`）时按不计睡眠的时钟计时；`Date` 是墙上时间。按这个理解，唤醒后 App 的续约循环已经到期，会在进程得到调度后立即执行；helper 的定时器还要走完睡前剩下的不到 15 秒，然后用 `Date` 比较，发现已过期。多数情况下 App 先到，但 App 的续约每次新建 XPC 连接并在 detached task 里调用，主线程繁忙或被 App Nap 推迟时可能晚于 helper。另外用户改系统时间、对时跳变也会让 `Date` 的截止时间提前或推后。

2.1 的改法：

- 截止时间改存不计睡眠的单调时间（`clock_gettime_nsec_np(CLOCK_UPTIME_RAW)` 或 `DispatchTime.now().uptimeNanoseconds`），涉及 `start()`、`renewLease`、`performSetLimit`、`tick()` 四处赋值或比较，以及 `status` 里的 `leaseRemainingSeconds`。
- 把“截止时间、续约、是否到期”做成 `BatteryCore` 里的一个小类型，时间由参数传入，写单元测试：续约后不到期；超过时长到期；`seconds` 被限制在 60–900。
- 改后的含义是“清醒状态累计 5 分钟没有续约才恢复”。App 崩溃后电脑立刻睡眠时，恢复会推迟到唤醒后 5 分钟。睡眠期间低于 80% 的上限是否仍然生效是 21.9 的待验证项，把这个后果写进设计文档 21.4。
- `idleExitInterval` 用的 `lastActivity` 也是 `Date`，唤醒后可能提前判定空闲并退出。有标记文件时不会走到这一步，影响小，可以一起改。

2.2 的改法：续约条件不看读回值，改为 `managedDesiredLimit` 低于 80，或校准进行中，或 helper 状态里 `hasMarker` 为真。helper 的 `renewLease` 在没有标记时本来就不做事，多续几次没有副作用。测试用例：目标 60%、系统临时充满期间读回为 100，仍然续约。

### 11.1 系统策略读取失败与没有策略混在一起（已读代码；实际影响为推断）

代码依据（路径均相对仓库根目录）：

- `Packages/HachibuKit/Sources/BatteryCore/PowerUIChargeLimit.swift:226`：`readUIState` 在接口类型编码不符、调用失败或返回错误时给出 nil。`canWrite`（第 105 行）只核对写入方法，策略读取失败不会直接关闭写入能力。
- 同文件第 50 行：`SystemChargeState.init` 只映射已知的特殊状态，其他状态也返回 nil。`BatterySnapshot.swift:213` 将它存入快照，没有保留“正常状态、未识别状态、读取失败”的区别。
- `Packages/HachibuKit/Sources/BatteryCore/ChargePolicy.swift:16`：只识别明确匹配的策略；强制充满标志为 nil 时也不计为活动策略。
- `Packages/HachibuKit/Sources/FeatureUI/BatteryMonitor+ChargeControl.swift:239`：活动策略为空就继续判断是否写入目标，没有单独检查策略读取是否成功。

触发条件：上限仍能读到、写入能力仍可用，但系统策略读不到或返回了未识别值，并且当前上限与目标不同。此时自动控制可能尝试写回目标。如果系统实际上正在临时充满或优化充电，就可能与“不干预系统策略”的规则冲突。代码路径可确认，系统是否接受写入、是否改变实际充电行为尚未复现。

建议：控制输入保留“已知无特殊策略、已知有策略、未知”，同时保留原始状态码、读取失败原因和采样时间。未知时如何暂停自动重写、何时重试，需写进设计后实施。用户主动修改、退出恢复、helper 崩溃恢复分别定规则，不能用一个总开关一律禁止，否则可能使校准的临时低上限无法释放。

建议验收：已知正常值可以正常控制；接口失败和未识别值不会被当作正常值；恢复读取后重新判断；已有临时状态的释放与恢复仍可执行。增加这些输入的组合测试，实际系统策略与写入的关系仍需真机确认。

与 10.2 一起看：用户目标、PowerUI 读回、powerd 登记和实际充放电行为应分别判断。当前 `evaluateManagedLimit` 在读回符合目标时直接结束判断（第 251 行），校准第 6 步的 `isTargetApplied` 也只比较读回（第 572 行）。登记缺失时要结合插电状态、系统策略和等待时长决定后续动作；不能一见没有登记就持续重写。

### 11.2 健康趋势没有按电池身份分段（已读代码；结果为静态推断）

代码依据：

- `Packages/HachibuKit/Sources/HistoryStore/HistoryStore.swift:302`：采集时会识别电池，并在变化时记录 `battery_changed`。
- 同文件第 156、184 行：`dailyHealth` 查询全部电池的数据，`mergeDaily` 按日期和来源优先级逐字段合并，没有按电池身份分组。`Records.swift:159` 的 `DailyHealth` 也不保留电池身份。

- 导入预览已经有不同电池提示（`HistoryStore/HistoryImport.swift:265`、`FeatureUI/SettingsPage.swift:460`），但提示不会改变后续合并与趋势计算。

可能影响：换过电池后，旧电池和新电池的容量会进入同一个趋势比较；导入不同电池的数据时，同一天还可能把一块电池的满充容量与另一块电池的循环次数合在一起。首尾循环次数减少时 `cyclesPerMonth` 会返回 nil，但这不能覆盖换电池后循环次数重新超过旧值等情况，也不能阻止容量趋势跨电池计算。

建议：在查询和图表数据中保留电池身份，按电池分段展示和计算趋势。同一电池的多来源仍可沿用现有优先级；身份未知的数据单独规定归属和展示方式，不凭日期自动认定为当前电池。此项涉及公共数据类型和可能的存储调整，实施前应明确范围。

另一个展示问题：`healthTrend` 要求首尾相隔至少 60 天，但每个 30 天比较窗口只需 5 个有效值（`HistoryChartData.swift:317`、第 348 行）。这符合现有算法，但稀疏记录与连续记录的结论可信度不同。建议展示窗口内的有效记录天数，是否提高门槛另行决定。

建议验收：同一电池的多来源合并保持原规则；换电池前后趋势分开；不同电池同日数据不交叉补字段；无序列号导入、稀疏记录不会产生确定的跨电池衰减结论。当前没有对用户数据库做复现。

### 11.4 小时汇总不足以还原高温、高电量时长（已读代码与数据限制）

`Packages/HachibuKit/Sources/HistoryStore/HistoryStore.swift:419` 的小时字段和第 431 行的聚合 SQL，保存了样本数、插电分钟数、充电分钟数，以及电量和温度等指标的平均、最小、最大值；没有按电量或温度阈值累计的样本数。聚合后原始分钟记录会删除。

平均、最小、最大值不能确定超过阈值的时长。例如各有 4 条等间隔温度记录：`30、30、40、40` 与 `30、35、35、40` 的平均值、最小值、最大值、样本数全部相同，但高于 38°C 的记录分别有 2 条和 1 条。因此 5.4 的功能建议需要新增数据，不能直接由现有小时表准确生成。

建议：先确定阈值与统计口径，再选择固定阈值累计或温度、电量分桶。若允许用户事后修改阈值，单个固定阈值累计值仍不足以重新计算任意阈值下的时长。每项指标应保留有效样本数，统计明确限于有记录的时段；缺失值和睡眠缺口不算作低温、低电量或零时长。

建议验收：聚合前后已定义指标一致；缺失值、睡眠缺口和不足一小时的数据处理正确；历史上没有累计字段的记录显示未知，不能补成 0，也不能从平均值推算精确时长。指标未决定前不为此修改数据库。

### 12.3 充满一次

**现状（已读代码和文档）**

- 设计文档第 6 节写明不做，理由是系统的 `temporarilyDisableMCL:` 期间读数为“开启，上限 100”，与用户设为 100 无法区分。本方案不调用这个方法，所以要先改这条结论，并说明原理由不适用的原因。
- 用户现在要充满，只能把档位改成 100%，充满后自己改回。接管模式下退出 App 也会恢复接管前的原值，不等于充满。
- 可以照搬的实现是“保持当前电量”：`ChargeLimitHold.action` 是纯函数，`BatteryMonitor.evaluateChargeLimitHold` 负责“先保存再写入”，`restoresChargeLimitHoldFirst` 负责启动时先恢复，`restoreChargeLimitHoldBeforeExit` 负责退出时同步恢复。

**建议规则**

- 开始：用户在面板或设置页点“充满一次”。条件：插电、可以写入、没有其他充电控制工具、`snapshot.activeChargePolicies` 为空、没有进行中的校准、当前上限为开启且低于 100。开始前把用户上限存进 UserDefaults，再写入关闭上限（`ManagedChargeLimit.change(for: 100)` 即 `.disable`）。进行中的“保持当前电量”先丢弃，做法同 `startCalibration`。
- 进行中读回为关闭：认为是自己的。读回变成别的开启值：认为用户改过，丢弃保存的值，不写入。读不到：等待，不写入。
- 结束并写回用户上限的条件，任一成立：电量 100% 且 `isCharging != true`；拔电；用户取消；超时；检测到其他充电控制工具；App 退出（同步写回）；App 启动时发现有保存的状态（先写回）。
- 系统策略出现时不写入，等它结束后再按上面的条件判断。
- 档位显示保存的用户上限，不显示 100%。状态文字需要一个新状态，与 `ChargeStatus.temporaryFullCharge`（系统的临时充满）分开，避免两者的恢复规则混在一起。

**与两种模式的衔接（最容易出错的地方）**

- 接管模式：`evaluateManagedLimit` 把读回与 `managedDesiredLimit` 不同视为被别处改过，会立刻写回目标。充满一次必须进入 `ManagedChargeLimit.desiredLimit` 的优先级（校准 > 充满一次 > 保持 > 目标），否则关闭上限后下一次读取就被改回。`managedAppliedLimit`、`hasRevertedExternalChange` 的提示逻辑不能把这次变化算成外部修改。
- 接管模式且目标低于 80%：`RoutedChargeLimitWriter` 写 `.disable` 时先调用 helper 的 `release()`，helper 会按标记文件恢复接管前的原值并删除标记；结束时写回目标要再经 helper `setLimit`。这期间 Helper 变为不可用，目标就写不回去，按 10.9 的建议这时按 80% 执行并提示。标记删除后 helper 不再有续约和超时恢复，App 在充满期间崩溃，上限会一直关闭到下次启动。这一点与 10.3 的规则 6 不一致，需要用户决定是否接受（失败的方向是多充电，不是停在低电量）。
- 跟随系统设置：没有目标，保存的用户上限就是开始前的系统值。结束写回后，如果用户选了“保持当前电量”，`ChargeLimitHold` 会按现有规则把上限写成 99 并保持，这符合用户的选项，不需要特殊处理，但要写测试确认两次写入之间不会互相丢弃状态。
- 用户在充满期间自己在系统设置里选 100%：与自己写的关闭区分不了，结束时会被写回原上限。写进设计文档。

**是否要等 10.3**（意见）：10.9 建议等模型改造之后做。重新看代码后的判断是不必等：保存用户上限、写临时值、按条件写回这部分逻辑在两种模型下相同；模型改造后要重做的只有接管模式的衔接点（上面第一、二条）。但建议等 1.3 的实验结论，因为它决定目标低于 80% 时写回是否可靠。

**测试**：纯函数测试参照 `ChargeLimitHoldTests`，覆盖开始条件、每个结束条件、读回被改、读不到、系统策略期间、启动先恢复。带 `BatteryMonitor` 的测试参照 `ChargeLimitHoldMonitorTests` 和 `ChargeControlMonitorTests`，用 `ChargeLimitWriter` 的假实现，覆盖两种模式、目标低于 80%、写入失败后 60 秒不重试、退出时同步写回。

**只能真机确认**：关闭上限后多久开始充电（设计文档 21.2 记录约 2 秒）；充到 100% 时 `percent` 和 `isCharging` 的实际读数顺序；从关闭写回低于 80% 的目标后登记是否正确；充满期间合盖睡眠后的表现。

### 12.4 过热停充

**现状（已读代码和文档）**

- `新功能需求.md` 第 1 节一直待定。2026-11-09 之后上限可以写成任意值，过热时把上限临时写成当前电量就能停止充电，由充电器给电脑供电，不增加循环次数。
- 写入方式与“保持当前电量”相同（临时值 = 当前电量），区别只有触发条件：保持是“没在充电且电量高于上限”，过热停充是“正在充电且温度高于阈值”，这时当前电量低于上限。
- 温度读数来自 `snapshot.temperatureCelsius`（SMC `TB0T` 叠加后的值）。面板关闭时约每 60 秒更新一次。

**建议规则**

- 触发：插电、正在充电、温度连续高于阈值一段时间。恢复：温度连续低于“阈值 − 回差”一段时间，或拔电。计时方式照 `TemperatureAlertRule`：读数缺失时两段计时都从头开始，相邻读数间隔超过 90 秒也从头开始。没有回差和持续时间会在阈值附近反复写入。
- 触发时临时值取当前电量（不超过 99）。恢复时写回用户上限。
- 读数长时间缺失时恢复，不能因为读不到温度一直停在临时值。时长由用户定。
- 校准期间不生效（AlDente 相同）。系统策略期间、其他充电控制工具运行时不写入。
- 与充满一次同时出现时的优先级需要定：建议过热停充优先，充满一次暂停计时并在界面说明。
- 用户上限为关闭（100%）时也要能用：保存的用户上限要能表示“关闭”，恢复时写 `.disable`。现有 `ChargeLimitHold` 只在上限开启时开始，`userLimit` 是整数，不能直接复用，建议与 12.3 一起设计一个临时状态类型，带种类（保持、充满一次、过热停充）、用户上限（可为关闭）和临时值。

**范围限制（已读代码）**

- 临时值不低于 80% 时经 PowerUI 写入，两种模式都能用，不需要 Helper。
- 临时值低于 80% 时要经 helper。`renewLeaseIfNeeded` 开头要求 `chargeControl.mode == .managed`，跟随系统设置时不续约，helper 5 分钟后会按标记恢复。所以第一版建议：跟随系统设置时只在电量不低于 80% 时生效；接管模式且 Helper 可用时任意电量生效。电量低于 80% 而不能生效时在界面说明原因。
- 低于 80% 的写入只在 macOS 27 开放（设计文档 21.2），这条限制同样适用。

**需要用户决定**：是否做；阈值是否与温度提醒共用（AlDente 默认 35°C，提醒默认 40°C，建议分开）；默认是否开启（建议默认关闭）；是否发通知。

**未验证**：macOS 自己在电池过热时是否已经暂停或降速充电（`ChargerData` 的 `TimeChargingThermallyLimited` 等字段含义未确认，见 `新功能需求.md` 待定事项）。如果系统已经在做，这个功能的价值是把阈值降到系统阈值以下。

**测试**：纯函数覆盖触发、恢复、回差、读数缺失、间隔过长、阈值变化；带 `BatteryMonitor` 的覆盖两种模式、电量低于 80% 时的范围限制、与保持当前电量和充满一次同时出现。真机确认：临时值等于当前电量时充电是否在几秒内停止；恢复后多久重新充电。

### 12.5 更多提醒

**现状（已读代码）**

- `BatteryAlert` 有温度过高、校准完成、校准暂停、上限未生效、系统校准开始；`lowHealth` 是保留的旧接口，不再发送。基于读数判定的规则只有 `TemperatureAlertRule` 一条。
- `AlertMonitor.handleReading` 只在完整读取后调用（`BatteryMonitor.update`），快速的 IOPS、SMC 读取不触发。面板关闭时判定最多晚约 70 秒，对下面三种提醒可以接受。
- `AlertMonitor.start()` 只在 `temperatureAlertEnabled` 打开且从未询问时请求通知授权。新提醒打开时也要走到请求授权。
- 已提醒状态存在 UserDefaults（`temperatureAlerted`），只在系统接受通知请求后才持久化，发送失败下次重试。新规则沿用这套做法，每种提醒用各自的通知标识符。

**候选**

| 提醒 | 触发 | 重置 | 注意 |
|---|---|---|---|
| 充电完成 | 本次插电期间状态第一次变成已达上限或已充满 | 拔电 | 启动时已经处于该状态不提醒，要有“上一次状态已知”的前提；“保持当前电量”和校准期间的临时上限不算 |
| 低电量 | 使用电池且电量不高于阈值（建议默认 20%） | 插电，或电量回到阈值 + 5 以上 | 系统在 10% 有自己的提示，价值在阈值可调 |
| 插电仍在放电 | 状态为 `pluggedInDraining` 持续若干分钟 | 状态结束 | 测试 fixture 里没有插电放电（`AGENTS.md`），先录 fixture 再做；优先级最低 |

- 充电完成的判断用 `ChargeStatus(snapshot)` 的结果，不要自己用电量和上限重新推一遍，否则会和面板状态文字不一致。
- 新提醒建议默认关闭，避免已有用户升级后突然收到通知（意见，用户决定）。
- 要改的地方：`AlertRules.swift`（新规则）、`AlertMonitor.swift`、`AppSettings.swift`（开关、阈值及其测试）、`SystemAlertNotifier.swift`（通知文案）、`NotificationsPage.swift`（设置行和预览）、String Catalog、`SettingsRenderTests.renderNotifications`、设计文档第 12 节。

**测试**：参照 `AlertRulesTests`、`AlertMonitorTests`。覆盖每种触发和重置、启动时已处于触发状态、读数缺失、通知未授权、发送失败后重试、开关关闭再打开。

### 12.6 快捷指令

**现状（已读代码）**

- 仓库里没有 AppIntents、URL scheme、命令行工具。最低系统 macOS 14，AppIntents 可用。
- 充电上限的两条写入路径：跟随系统设置时调用 `BatteryMonitor.setChargeLimit(_:)`；接管模式下这个方法直接返回（开头的 guard），界面改的是 `AppSettings.managedChargeLimit`，经 `AppDelegate.syncChargeControl` 同步后由 `evaluateManagedLimit` 写入。面板档位怎样在两条路径之间选择，在 `PanelRootView.swift`，没有读；意图要复用同一段选择逻辑，必要时把它提成一个函数，不能另写一份。
- `BatteryMonitor` 和 `AppSettings` 由 `AppDelegate` 持有。`BatteryMonitor` 在数据库打开之后才创建（`applicationDidFinishLaunching` 里的异步任务），App 被系统为执行意图而启动时，意图可能先于它就绪。

**建议范围**

- 读取电池状态：返回电量、是否插电、是否充电、充电上限、温度、系统功率。缺失的值返回空，不返回 0。
- 设置充电上限：参数为百分比。超出当前可用范围、不能写入、其他充电控制工具运行、目标低于 80% 而 Helper 不可用、上一次写入未完成时返回明确的错误，不自动改成别的值。跟随系统设置时写入后检查 `chargeLimitWriteFailed`；接管模式下保存目标即返回，结果里说明“已保存，等待生效”，不等待读回。
- “充满一次”的动作等 12.3 做完再加。

**先做的验证（未验证，我的理解）**：ad-hoc 签名、未沙盒、`LSUIElement` 的 App 定义的意图应当能出现在“快捷指令”里，前提是意图类型定义在 App target（不是 Swift Package）里，构建时生成元数据。当前构建日志里有 `Metadata extraction skipped, no AppIntents.framework dependency found`，说明加入意图后这一步会开始执行。先加一个只返回电量的意图，用 `scripts/build.sh` 打包后在 `dist/` 里运行，确认它在“快捷指令”里出现并能执行；不出现就停下来报告，不要为此改签名或加 entitlement。

**其他注意**：意图在 App 进程内执行，`perform()` 标 `@MainActor`；等 `BatteryMonitor` 就绪要有超时。意图的名称和说明要本地化，放在 App target 的 `Localizable.xcstrings`。新增文件后要运行 `xcodegen generate`。

**测试**：写入路径的选择逻辑提成函数后在 `FeatureUITests` 里测；意图本身只能在真机上从“快捷指令”运行确认。

### 12.7 菜单栏多读数

**现状（已读代码）**

- `MenuBarContent` 是单选枚举（电量、系统功率、温度），存在 UserDefaults 的 `menuBarContent`。`MenuBarTitle.string` 生成文字，`StatusItemController.updatePresentation` 写到按钮标题。iOS 样式且选电量时标题为空，电量数字画在电池图标里。按钮字体已经是等宽数字。
- `新功能需求.md` 第 4 节把“多项同时显示、任选组合并排序”列为后续范围。

**建议**

- 设置改为有序的多选，存到新键；读不到新键时用旧键的单个值迁移，旧键保留不删，方便用户装回旧版本。
- 标题按顺序用固定分隔拼接。iOS 样式下电量已经在图标里，拼接时去掉电量这一项，无障碍文字仍然读全部项。
- 允许一项都不选（只显示图标）要单独决定；现在 iOS 样式选电量时已经是只显示图标。
- 要改的地方：`AppSettings.swift`、`MenuBarTitle`、`StatusItemController.swift`、`SettingsPage.swift` 的菜单栏设置（没有读）、`AppSettingsTests`、设计文档第 9、13 节、`新功能需求.md` 第 4 节。排序用拖动还是固定顺序由用户定；固定顺序实现最简单。

**只能真机确认**：三项同时显示时的宽度，在有刘海的屏幕上是否被系统隐藏；数值变化时宽度是否跳动。

### 12.8 长期统计

11.4 已说明现有小时汇总算不出高温、高电量时长。补充实施顺序：

- 分两步，存储先做。分钟数据保留 7 天后聚合成小时数据并删除（聚合 SQL 在 `HistoryStore.hourlySelect`），聚合时没有记下的分布以后补不回来。先给小时表加分桶计数，界面可以晚做。
- 建议分桶而不是单一阈值，这样以后改阈值不用重新采集：电量按区间计样本数，温度按区间计样本数，另存每项的有效样本数。区间边界需要用户确认后再建表，建了之后改边界等于旧数据作废。
- 数据库迁移新增一个版本，只加列。已有的小时记录这些列为 NULL，界面上显示为未知，不能当 0。迁移时还没聚合的分钟数据（最近 7 天）会在之后聚合时自然带上分桶。
- `HistoryStore.aggregate` 的调用流程和事务边界没有读，实施前要读，确认聚合和删除在同一个事务里。
- 界面放在历史页哪里、用什么图，走设计文档 19.1 的流程，另行决定。

**测试**：参照 `HistoryStoreTests` 里现有的聚合测试。覆盖分桶边界值、缺失值不计入、跨小时、迁移后旧记录为 NULL。

### 12.9 真机验收

`充电接管与校准验收.md` 的验收表除“调用方和更新”一行外都是待真机确认，这些功能从 v0.1.8 起已公开发布。这是当前最大的稳定性风险，也是 12.3、12.4 的前提。建议用户按那张表逐行做，每行保留操作时间、诊断导出和日志；1.3 的实验（步骤在 10.2）与其中“唤醒和重启”一行重合，可以一起做。AI 能做的只有整理步骤和分析导出的日志，不能代替真机操作。

### 12.10 面板打开时的 CPU

设计文档 19.8 记录：2026-10-26 Debug 构建下面板打开时 CPU 从 45–50% 降到 32–35%，之后又做了水面静止、光点降到 15 帧、读取间隔放宽，但“这一轮改动后的 CPU 尚未复测”。建议用户用 Release 构建在面板打开状态下看活动监视器的 CPU 和能耗影响，记下数值。数值仍然偏高再决定改动，可改的地方是光点动画的帧率和 2.5 秒一次的 SMC、IOPS 读取触发的重绘范围。这一项与第 4 节（面板关闭时的轮询）分开测。
