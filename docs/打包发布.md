# 打包发布

本文记录 Hachibu 的打包和发布步骤，做法与 cc-bar 相同：ad-hoc 签名，不需要付费 Apple Developer 账号和公证；推送 tag 后由 GitHub Actions 构建并发布 Release；Sparkle 从 Release 附件读取 appcast。

显示版本和 Sparkle 比较的构建版本都使用 `Config/Base.xcconfig` 里的 `MARKETING_VERSION`（`CURRENT_PROJECT_VERSION = $(MARKETING_VERSION)`）。发布版本按 `X.Y.Z` 逐版递增，必须与 tag `vX.Y.Z` 一致。

## 1. 本地打包：`scripts/build.sh`

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer   # 一次性，确保指向完整 Xcode
brew install xcodegen                                              # 一次性
# 一次性：安装 DMG 打包工具 dmgbuild，见 packaging/dmg/README.md
SPARKLE_PUBLIC_ED_KEY="已配置的公钥" ./scripts/build.sh               # 产物: dist/Hachibu.dmg + dist/Hachibu.app.zip
```

- 脚本先运行 `xcodegen generate`，再清空 `build/`，用 `CODE_SIGNING_ALLOWED=NO` 做 Release 构建，然后按 Sparkle 的 XPC services、Autoupdate、Updater.app、framework、外层 App 的顺序逐层 ad-hoc 签名（带 Hardened Runtime）。签名时不使用 `--deep`；最后用 `codesign --verify --deep --strict` 验证整个包。
- 正式打包必须传入有效的 `SPARKLE_PUBLIC_ED_KEY`，写入 App 的 `SUPublicEDKey`。未配置时脚本在构建前停止。`Config/Base.xcconfig` 保存同一个公钥，供本地 Xcode 构建使用；CI 用 GitHub variable 显式传入，发布生成器会验证 App 与 CI 公钥一致。
- 不使用 Developer ID 证书和公证。ad-hoc 签名没有 Team ID，`App/Hachibu.entitlements` 关闭 Library Validation，否则 Hardened Runtime 会拒绝加载 Sparkle framework；这与 Sparkle 的 EdDSA 更新包验证是两回事。首次手动安装仍受 Gatekeeper 拦截，用户要按 README「安装」一节放行一次。
- 产物固定在 `dist/Hachibu.dmg` 和 `dist/Hachibu.app.zip`（`dist/` 已 gitignore）。DMG 用于首次手动安装，由 `scripts/package-dmg.sh` 用 dmgbuild 加上背景图、卷图标和 Applications 快捷方式；ZIP 用于应用内自动更新。
- 想检查打包结果，在 `dist/` 或临时目录里查看，不要直接替换 `/Applications/Hachibu.app`。
- 不要用 Xcode 的 Product → Archive 导出分发，那样会绑定本机开发证书。

## 2. GitHub Actions 自动发布

[.github/workflows/release.yml](../.github/workflows/release.yml)：推送 `v` 开头的 tag 后，macOS runner 依次校验更新签名配置和发布说明，安装 XcodeGen 和 dmgbuild，执行 `scripts/build.sh`，用 SPM artifact 里与 App 同版本 Sparkle 的 `sign_update` 签名，上传全部产物到 draft Release，最后改为正式并标记为 latest。只有上传完整后，新的 appcast 才对用户可见。

Release 包含四个产物：

- `Hachibu.dmg`：手动安装包。
- `Hachibu.app.zip`：由 App 内置公钥验证的自动更新包。
- `appcast.xml`：已签名的 Sparkle 更新源，含版本、最低 macOS、arm64 硬件要求、固定版本 ZIP 地址、大小、包签名和更新说明地址。
- `release-notes.md`：应用内显示的更新说明，已签名；内容与 Release 正文一致：本版说明在前，后面是 `release-notes/highlights.md` 的近期新功能（为空则没有），HTML 注释已移除。

更新源地址固定为 `https://github.com/nanvon/hachibu/releases/latest/download/appcast.xml`（`Config/Base.xcconfig` 的 `SPARKLE_FEED_URL`）。GitHub 的 `releases/latest/download/<文件名>` 总是指向最新正式 Release 的同名附件，所以不需要 GitHub Pages。安装包和更新说明引用 `releases/download/vX.Y.Z/...` 的固定版本地址，避免检查后下载到另一版。

生成器 `scripts/generate-update-feed.py` 校验 tag、App 版本、更新源、公钥与签名配置，用 `lipo -archs` 读取主执行文件架构，再用 App 内置公钥验证最终 ZIP 的签名（`scripts/verify-update-signature.swift`），阻止公私钥不匹配的产物发布，之后签名更新说明和 appcast。**签名后不得修改这些文件或重新压缩 ZIP**。App 配置了 `SURequireSignedFeed` 和 `SUVerifyUpdateBeforeExtraction`，只接受经过验证的更新源和更新包。

runner 镜像默认的 Xcode 可能比本地旧，用旧 SDK 编译会缺少 `NSGlassEffectView` 等新接口。workflow 用 `maxim-lobanov/setup-xcode@v1` 选择 `latest-stable`。

另有 [.github/workflows/ci.yml](../.github/workflows/ci.yml)：推送到 `main` 和提交 PR 时编译、测试 HachibuKit，并不签名编译 App。

## 3. 首次配置更新签名密钥

只需配置一次，在首次发布前完成。**普通发版不要重新生成或更换密钥**：已安装用户信任的是 App 内置的公钥，私钥丢失后只能让用户手动重装。

1. 本机解析完 SPM 依赖后，找到 Sparkle artifact 的 `bin/generate_keys`，例如 Xcode DerivedData 的 `SourcePackages/artifacts/sparkle/Sparkle/bin/`，或运行 `scripts/build.sh` 后的 `build/SourcePackages/artifacts/sparkle/Sparkle/bin/`。
2. 运行 `generate_keys --account hachibu`。私钥保存在登录钥匙串，终端显示公钥；同账户已有密钥时会复用，不覆盖。再次查看公钥用 `generate_keys --account hachibu -p`。
3. 在 GitHub 仓库 **Settings → Secrets and variables → Actions → Variables** 添加 `SPARKLE_PUBLIC_ED_KEY`，值为公钥；同一个值填入 `Config/Base.xcconfig` 的 `SPARKLE_PUBLIC_ED_KEY` 并提交。
4. 用 `generate_keys --account hachibu -x <安全的备份路径>` 导出私钥，在 **Secrets** 添加 `SPARKLE_PRIVATE_ED_KEY`，值为该文件内容。私钥只经标准输入交给签名工具，不进入参数、构建设置、仓库或日志；导出文件放在受保护的位置并备份（例如密码管理器）。
5. 缺少 variable 或 secret 时，CI 在构建前失败；格式或配对错误时，CI 在创建 Release 前失败。

密钥生成、钥匙串访问和 GitHub 配置由维护者手动执行，普通代码修改不执行这些操作。

## 4. 发版

```bash
git push origin main
git tag v0.1.0          # 与已提交的 MARKETING_VERSION 一致
git push origin v0.1.0
```

- 发版前先写 `release-notes/vX.Y.Z.md`，规则见 [release-notes/README.md](../release-notes/README.md)。缺少这个文件时 CI 不创建 Release。
- tag 只是给已提交的版本打标记，不改版本号。打错 tag 可撤销：`git tag -d vX.Y.Z && git push origin :vX.Y.Z`。
- AI 代为发版的固定步骤见 [AGENTS.md](../AGENTS.md) 的「标准发布流程」。
