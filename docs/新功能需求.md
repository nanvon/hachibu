# 新功能需求

记录日期：2026-10-25。

本文记录用户提出的功能、可行性判断与实施进度。未确定的部分只是需求和调研结论，不是实施设计；决定要做后再写进 `v1技术设计.md` 对应章节。AlDente 的信息来自本机 AlDente 1.39.3 安装包的本地化字符串和资源名（只读查看），以及官方功能说明页，没有反编译。

## 1. 电池温度过高时停止充电

AlDente 的“过热保护”（Pro 功能，需要它的 helper）：电池温度超过设定值（默认建议 35°C）时停止充电，降到阈值以下后恢复，校准期间不生效。[官方说明](https://apphousekitchen.com/feature-explanation-heat-protection/)

Hachibu 的现状和限制：

- 唯一的写入途径是 PowerUI 的系统充电上限，范围 80%–100%（第 6 节）。电量低于 80% 时没有办法用它停止充电。
- 电量 ≥ 80% 时，理论上可以在过热时把上限临时改成 80%，冷却后改回。代价是 Hachibu 会改动用户在“系统设置 → 电池”里看到的值，并且要记住原值、在退出和崩溃后恢复。这和第 6 节“Hachibu 没有自己的充电状态”的规则冲突。
- 任意电量都能停止充电，在本机只能靠 SMC CHIE（切断适配器供电，电脑改用电池），需要 root helper。2026-10-26 root 探测确认暂停充电的 key 无法访问，已决定不做 helper 和 SMC 后端（设计文档第 18 节、`v2充电控制技术调研.md`）。
- macOS 自身在电池过热时会暂停或降速充电。本机 `ChargerData` 里有 `TimeChargingThermallyLimited`、`SlowChargingReason`、`NotChargingReason`，含义未公开，目前只写进诊断导出。

可做的部分：

| 方案 | 前提 | 说明 |
|---|---|---|
| 显示系统温控限充 | 先在充电、过热状态下采样，确认上述字段的含义 | 面板或状态文字提示“系统因温度限制充电”。第 7 节规定 `NotChargingReason` 不参与状态判断，要改需另行决定 |
| 已有的温度提醒 | 无 | 第 12 节已实现，可以在提醒文案里说明“系统会自行限制充电” |
| 过热时临时降低系统上限 | 用户接受修改系统设置，并接受需要恢复原值 | 只对电量 ≥ 80% 有效，需要设计恢复规则 |
| 真正的过热停充 | root helper + SMC | 不做：本机只能用 CHIE 强制放电，已决定不做 helper（2026-10-26） |

待定：是否接受“临时降低系统上限”这个半有效的方案；不接受就不做。

## 2. 系统功率（SystemLoad）的含义

`PowerTelemetryData.SystemLoad` 是电脑本身消耗的功率，不包含充入电池的功率。

- 充电时：`SystemPowerIn ≈ SystemLoad + BatteryPower`（BatteryPower 为正）。第 5 节在插电未充电状态实测 14514 = 14514 + 0。
- 使用电池时：本机 2026-10-25 读数 `SystemLoad = 13336`，`BatteryPower = -13336`，两者绝对值相等。
- 面板功率流向图里“电脑”节点显示的就是它，对应 AlDente 截图里的“MacBook 24.2 W”。

现有设计不需要改。

## 3. 功率细分（参考 AlDente Power Flow）

AlDente 的 Power Flow 节点共 7 个（本地化键 `pfNode*`）：电源适配器、电池、MacBook、SoC、显示、USB、其他。用户提供的截图已包含全部 7 个，电池在放电时位于左侧，充电时应在右侧。截图中 SoC 4.7 + 显示 1.5 + USB 0.0 + 其他 17.9 = 24.1 W，与 MacBook 24.2 W 相差 0.1 W，说明“其他”是用总功率减去前三项得到的差值。截图里电源适配器 < 1 W、电池放电 21.7 W，是 AlDente 切断了适配器供电（放电或 CHIE），不是正常插电状态。

AlDente 二进制中能看到的线索：链接了 `libIOReport.dylib` 并有 `IOReportHelper` 类；字段名 `socPowerRaw`、`displayPowerRaw`、`usbPowerRaw`、`systemLoadRaw`、`acInputPowerRaw`、`batteryPowerRaw`；SMC key 字符串 `PSTR`、`PDTR`、`PDBR`、`PCBC`。具体哪个字段读哪个来源没有确认。

### 3.1 本机实测（2026-10-25）

环境：MacBookPro18,1（M1 Pro），macOS 27.0.1，使用电池（未插电），AlDente 1.39.3 在运行。用独立的 C 探针（不在仓库里）以普通用户身份运行，没有 sudo。SMC 只发 READ_INDEX、READ_KEYINFO、READ_BYTES，没有写入。IOReport 订阅 “Energy Model” 分组，按 1、5、10、15 秒间隔取两次样本求差。同时读 `PowerTelemetryData` 做对照。

SMC：本机共 2179 个 key，P 开头的 key 都是 `flt `（4 字节浮点，小端）。

| key | 读数 | 判断 |
|---|---|---|
| `PSTR` | 24.9–39.7 W，每秒都在变化 | 实时系统总功率。负载平稳时与 `SystemLoad`（26.0–29.1 W）接近；负载升到 37.7–39.7 W 时，`SystemLoad` 仍是 60 秒前的 26.0 W |
| `PPBR` | 23.2–40.7 W，随 `PSTR` 变化 | 电池功率（本次为放电），数值为正 |
| `PDTR` | 约 0（原始值约 5e-5） | 不插电时为 0，与“直流输入功率”的含义一致；插电时未测 |
| `PDBR` | 1.19–1.29 W，基本不变 | 很可能是屏幕背光功率，与 AlDente 截图中“显示 1.5 W”量级一致；未改变亮度验证 |
| `PCBC` | KeyInfo 失败，本机没有这个 key | AlDente 二进制中有这个字符串，作用不明 |
| `PU1C`、`PU1R`、`PU2C`、`PU2R` | 全为 0 | 名字可能和 USB 口有关；测试时没接 USB 设备，无法判断 |

IOReport “Energy Model”：

- `GPU Energy`（驱动 `AGXAcceleratorG13X`，单位 nJ）：实时更新，3.5–5.5 W。
- CPU、ANE、DRAM、ISP、AVE 等通道（驱动 `AppleT6000PMGR`，单位 mJ）：1–15 秒间隔的差值都是 0。原始数据里的时间戳和计数在 15 秒内不变；连续观察 7 分钟只更新了一次，两次更新间隔分别为 301 秒和 353 秒，对应的 CPU 平均功率为 4.85 W 和 5.77 W。
- 结论：本机用普通用户权限只能拿到实时的 GPU 功率，CPU 等部分只有约 5 分钟的平均值，跟不上面板每 10 秒的刷新。是否有其他客户端触发了这次更新、其他机型是否同样如此，都没有确认。

未验证：插电和充电时各 key 的读数和符号；调节亮度后 `PDBR` 是否随之变化；接 USB 设备后 `PU*` 是否变化；Hardened Runtime 加 ad-hoc 签名的 App 内能否同样读取（探针没有签名）。

### 3.2 可行性

| 节点 | 来源 | 权限 | 状态 |
|---|---|---|---|
| 电源适配器、电池、电脑 | `PowerTelemetryData`（已用） | 普通用户 | 已实现 |
| 电脑（实时） | SMC `PSTR` | SMC 读取，普通用户 | 2026-10-26 起作为系统功率的实时来源（5.1 节） |
| SoC | IOReport “Energy Model” | 普通用户，私有库 | GPU 实时；CPU 等约 5 分钟才更新一次，无法实时显示 |
| 显示 | SMC `PDBR` | SMC 读取，普通用户 | 本机可读，含义待调节亮度确认 |
| USB | 可能是 SMC `PU*` | SMC 读取，普通用户 | 待接 USB 设备验证 |
| 其他 | 总功率 − SoC − 显示 − USB | — | 与现有规则冲突，且依赖 SoC、USB 的来源，见下 |

需要先决定的问题：

- 第 3 节规定 v1 不读 SMC，不做残差显示；AGENTS.md 也写了“不要做配平计算”。“其他”本身就是残差。要做就得改这两条规则。
- `SystemLoad` 约每 60 秒刷新一次。细分要和实时数值相减，总数应改用 `PSTR`；`SystemLoad` 仍作为“电脑”节点的原始读数，两者不混用。
- SoC 没有实时来源。可选：只显示 GPU 实时功率；或者显示 CPU 等部分的 5 分钟平均值并标注；或者不做 SoC 节点。AlDente 截图中的 SoC 4.7 W 来源不明，可能也是平均值。
- IOReport 和 SMC 读取都只在面板打开时运行，避免后台耗电。

建议顺序：先在插电、充电状态下重测，并调节亮度确认 `PDBR`；再决定是否放开读取 SMC，放开后先加实时总功率（`PSTR`）和显示（`PDBR`）；SoC 和“其他”等来源确定后再定。

## 4. 菜单栏图标样式

AlDente 的选项（设置 → 外观 → 菜单栏，部分为 Pro）：

| 样式 | 资源名 | 内容 |
|---|---|---|
| AlDente 状态 | `aldente_style`、`aldente_battery_charging/discharging/pause/unplugged` | 品牌图形，按充电、放电、暂停、未插电切换 |
| iOS 原生 | `ios_style`、`iOS_battery_bolt/plug/tip` | 实心电池，电量数字写在电池里，带闪电或插头 |
| macOS 原生 | `macos_style`、`macOS_battery_bolt/plug` | 与系统电池图标相同的外框 + 填充 |
| macOS 原生（彩色） | `macos_style_colored` | 同上，按状态着色 |
| 仅 AlDente 图标 | — | 只显示 logo |

另有：显示或隐藏百分比；低电量模式时图标变黄（`LPMColor`）；Pro 的“菜单项目录”，可以同时放多个读数（电量、温度、功率、硬件电量等）、拖动排序、隐藏单项图标、调整间距和刷新间隔；菜单栏数值保留一位小数。

Hachibu 当前实现（2026-10-26 已真机验收）：只保留 macOS、iOS 两种电池样式，默认 macOS，以 macOS 27、iOS 27 为外观参考。旁边仍是一项文字（电量、系统功率或温度三选一，`MenuBarContent`）；iOS 选择电量时只在电池内显示数字。旧 `brand`、`batteryColored`、`hidden` 及未知样式回退 macOS，原 `battery`、`ios` 和读数选择保留。实现规则见 `v1技术设计.md` 第 9、13 节。

素材来源核对（2026-10-25）：

- [Apple Design Resources](https://developer.apple.com/design/resources/) 提供 iOS 27、macOS 27 官方 UI Kit；其[许可](https://developer.apple.com/support/downloads/terms/apple-design-resources/Apple-Design-Resources-License-20230621-English.pdf)第 2.A、2.B 节限定设计稿用途，禁止嵌入软件。没有把其中的电池组件装入应用。
- iOS 27 的主体尺寸和端帽参照 Apple 发布的 [Sketch UI Kit](https://www.sketch.com/s/04c24d8b-38fb-4afb-8836-36617e022f02) 中 `System / Status Bars / iPhone 18 Pro / Light Background` 的 Battery 图层；macOS 27 参照本机 ControlCenter 的电池图层。原始参考只存临时目录，不进仓库，也不在运行时加载。macOS UI Kit 的菜单栏示例没有电池，未把它作为电池来源。
- AlDente 安装包包含 `macOS_battery_*`、`iOS_battery_*` 图片，但其[公开许可](https://github.com/AppHouseKitchen/AlDente-Battery_Care_and_Monitoring/blob/master/LICENSE)没有授予把这些图片放进另一应用再分发的权限，未复制进仓库。
- 用户确认按官方外观绘制、保留电池内百分比。当前实现用超椭圆方程独立生成主体，独立绘制端帽、闪电、竖向插头和系统字体数字，未复制参考的贝塞尔控制点。macOS 主体 23×12pt，iOS 主体约 26.33×13.67pt；颜色和填充规则见技术设计第 9 节。它们是参考系统外观的自绘实现，不称为 Apple 官方组件。

实施进度及后续范围：

1. 已实现：macOS / iOS 两种样式、固定画布、实际电量填充、充电闪电与插电未充电插头、低电量模式着色、1×/2× 离屏渲染与外观监听。标记直接根据 IOPS 插电、充电字段切换；插电放电也显示插头，不再被更新较慢的负功率读数隐藏。面板充电状态判断不变。通知层增加专门的插拔通知；采样层先在独立任务读取 IOPS 状态、短时补读，再安排完整采样，并合并重复请求、拦住旧结果覆盖。快速更新不增加温度提醒或写库频率。已有慢读取和乱序返回的回归测试，实际插拔响应已在真机上验收。
2. 检查：从实际绘制代码导出深浅外观下的充电、暂停、低电量、低电量模式、0%/100%/未知电量图，并核对参考主体轮廓；数字和各状态标记是独立绘制，不与系统逐像素一致。菜单栏已在真机上验收。
3. 后续范围：多项同时显示，电量、功率、温度任选组合并排序。

## 5. 实时数据与充电控制扩展（2026-10-26）

起因：切换充电上限后，面板和菜单栏要等约一分钟才反映充电状态变化，有时整段充电都没有显示。原因见 `v1技术设计.md` 5.1：IORegistry 和 IOPS 的读数只在约每 60 秒一次的刷新点上更新，SMC 每秒更新。

### 5.1 数据实时更新（第一阶段，不需要 helper）

需求：

- 读 SMC 用于实时显示，只发 KeyInfo 和 Read，读取模块里不能有写入代码；校验 key 的类型和长度，不符视为读不到，退回 IORegistry / IOPS。
- 面板打开时面板上所有数据每秒刷新；面板关闭时至少每 1–2 秒读一次 `CHSC`，充电状态变化后菜单栏图标马上更新；切换充电上限后约 10 秒内加快读取。
- SMC 读取放在采样 actor 之外，不被 PowerUI 或数据库写入阻塞。
- 状态判断和功率流向图优先用 SMC 数据，不做配平。
- 实测确认 `B0AP` 放电时的符号。

进度（2026-10-26）：已实现。文档见 `v1技术设计.md` 第 3、5.1、7、8、9、14、15、16 节和 AGENTS.md；代码为 `BatteryCore/SMC.swift`、`FeatureUI/BatteryMonitor.swift`。拔电实测确认 `B0AP` 放电为负。未在真机上验收菜单栏和面板的实际刷新，也没有测面板关闭时每 1.5 秒读取的耗电。

### 5.2 在 80%–100% 之间保持任意电量（第二阶段，不需要 helper）

需求：先验证 PowerUI `setMCLLimit:` 能否写入不在档位上的值（如 87）。能写入时，电量高于上限提供两个选项：“放电到上限”（系统默认行为）和“保持当前电量”（把系统上限临时写成当前电量，由充电器给电脑供电）。分开保存用户设置的上限和应用临时写入的值；拔电、关闭保持、应用退出或启动时恢复成用户设置的上限。不能写入时停止，不用别的办法凑。

验证（2026-10-26）：87 写入成功，PowerUI 和 SMC `CHLT` 都读回 87，2 秒后开始充电，写回 80 后 1 秒内停止，记录见 `v2充电控制技术调研.md`。用户确认：选项放在设置页常驻，默认放电到上限；电量 100% 时临时上限写 99。规则见 `v1技术设计.md` 第 6 节。

进度（2026-10-26）：已实现，单元测试覆盖开始保持、拔电和改选项时恢复、启动时先恢复、系统设置改过时只丢弃、保持期间改档位和关闭、退出时同步恢复、写入失败。面板“保持在 87%”的渲染图待用户确认；真机上的插拔、退出和崩溃恢复未验收。

### 5.3 特权 helper、插着电放电、校准模式（第三阶段）

需求：先验证 ad-hoc 签名加 Hardened Runtime 的应用能否用 `SMAppService.daemon` 注册 LaunchDaemon，以及 root 能否写放电 key（先查 `CHIE`）；任一项不通过就停止。两项都通过才实现：helper 只通过 XPC 提供开始放电、停止放电、查询状态；校验调用方；客户端断开、应用退出或崩溃（租约超时）、电量低于安全下限时自动恢复充电器供电；卸载前先恢复供电。功能为插着电放电到目标电量，以及校准模式（充到 100% → 插电放电到约 10% → 再充到 100% → 恢复原上限）。

进度：未开始。

### 5.4 不做：低于 80% 的上限

本机不能暂停充电（`CH0J`、`bfF0`、`bfD0`、`bfE0` 在 root 下也返回 `kIOReturnNotPrivileged`，`CH0B`、`CH0C`、`CHTE`、`CHWA`、`BCLM` 不存在），只能靠反复切断充电器供电维持低于 80% 的电量，会增加循环次数。复查方法：固件或系统更新后，用同一只读探针（只发 KeyInfo 和 Read）在 root 下查这几个 key，不再返回 `kIOReturnNotPrivileged` 时重新评估。

检测到 AlDente 等充电控制工具运行时不启用控制，这条规则保留。
